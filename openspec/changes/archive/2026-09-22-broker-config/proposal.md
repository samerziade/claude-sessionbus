## Why

Configuration today is scattered and env-only: `CHANNELS_HOME` is read at module scope in
both `broker/src/index.ts` and `bus/src/index.ts`, the transport mode is baked into the MCP
registration by `Makefile`'s `mcp-add` (`-e SESSIONBUS_TRANSPORT=socket`), and there is no
file-backed layer at all. The upcoming Matrix bridge work (see
`docs/superpowers/specs/2026-09-22-sessionbus-matrix-bridge-design.md`, decision D11) adds
seven-plus new knobs and one secret (a homeserver URL, an appservice token command, a root
space, an owner, a namespace prefix, an unread cap, a project-slug override map). None of
that belongs in a world-readable launchd plist regenerated by the Makefile, and env-only
configuration has no way to express a nested `matrix` block or a `projects` map at all. This
change builds the configuration layer now, ahead of the bridge itself, so the bridge is
built on a real config seam instead of `process.env` reads that would need retrofitting
later.

## What Changes

- A new pure `resolveConfig({ file, env, home })` in `broker/src/config.ts`: layers
  built-in defaults → `~/.claude/sessionbus/config.json` → environment (environment wins),
  performs no I/O and never reads `process.env` itself, and returns a typed `Config` plus a
  list of `ConfigProblem`s (each carrying a `severity` of `warning` / `invalid` / `fatal`)
  instead of throwing.
- Each resolved field also gets a **source** (`default` / `file` / `env`), so the broker can
  answer "where did this value come from."
- Unknown keys in the config file produce a `warning` problem and are otherwise ignored — a
  newer config file cannot brick an older broker.
- An invalid `matrix` block produces an `invalid` problem and forces `matrix.enabled` to
  `false` in the resolved `Config` — the bridge is disabled, and the broker keeps running.
  Only unusable **core** configuration (e.g. an empty/non-string `channelsHome`) produces a
  `fatal` problem.
- The broker entrypoint (`broker/src/index.ts`) resolves configuration once, before it binds
  its socket. A `fatal` problem routes through the existing `createFatalGuard` (from
  `broker-fail-loud`) and exits the process non-zero, before the broker starts serving —
  **BREAKING for the fail-loud contract's trigger set**, which gains a new, non-runtime
  trigger (see Capabilities below). `invalid` and `warning` problems are logged and do not
  exit.
- A new `broker config` subcommand prints the resolved configuration with each field's
  source and the Matrix secret redacted, regardless of which layer it came from.
- A separate, I/O-performing secret-resolution step runs the configured `tokenCommand` and
  uses its trimmed stdout as the Matrix bridge token; `SESSIONBUS_MATRIX_AS_TOKEN` overrides
  it (skips running the command) for tests and one-off runs. A `tokenCommand` that fails to
  run or exits non-zero is treated the same as an invalid `matrix` block (bridge disabled,
  broker keeps running) — the design doc does not say what happens on command failure; this
  proposal fills that gap (see design.md Open Questions / this agent's report for the exact
  wording change proposed upstream).
- `bus/src/index.ts` resolves the same shared config (imported across the workspace the way
  `broker/src/daemon.ts` already imports `bus/src/registry.ts`) and passes the resolved
  `transport` mode and socket path into `createTransport`, so the MCP registration no longer
  needs `-e SESSIONBUS_TRANSPORT=$(TRANSPORT)`. `createTransport`'s own `mode` option and its
  existing env fallback are unchanged, for backward compatibility with direct callers and
  existing tests.
- The launchd plist template (`broker/launchd/broker.plist.template`) already carries only
  `CHANNELS_HOME` — this change adds no new plist variables, keeping it that way is simply
  confirmed as a constraint for future (Matrix) changes, not a code change here.

**Out of scope:** Matrix naming/provisioning, the outbound mirror, the inbound relay,
`read_history`. This change lands the configuration seam only; nothing here starts a Matrix
client or validates reachability against a real homeserver.

## Capabilities

### New Capabilities

- `broker-configuration`: layered configuration resolution (defaults → file → environment)
  as a pure function returning a typed `Config` and a list of severity-tagged problems;
  per-field source reporting; the `broker config` diagnostic subcommand; Matrix secret
  resolution via `tokenCommand`/`SESSIONBUS_MATRIX_AS_TOKEN`; and `bus` consuming the same
  resolved configuration for its transport selection. This is genuinely new surface area —
  it spans both the `broker` and `bus` packages (config.ts is imported across the workspace
  boundary the same way `daemon.ts` already imports from `bus/src/registry.ts`), and its
  shape (pure resolver, severity-tagged problems, per-field provenance) doesn't fit the
  existing `broker-lifecycle` capability, whose requirements are about the supervised
  process's start/bind/exit contract, not about where its settings come from.

### Modified Capabilities

- `broker-lifecycle`: the "Supervised broker fails loud on unrecoverable errors"
  requirement gains one new trigger — a `fatal`-severity configuration problem detected at
  startup, before the broker opens its listening socket, exits the process non-zero exactly
  like the existing runtime triggers (post-listen listener error, uncaught exception,
  unhandled rejection). The existing three scenarios are unchanged; one scenario is added.
  `invalid`/`warning` config problems are explicitly **not** a new trigger — that boundary is
  owned by `broker-configuration`, not restated here.

## Impact

- **Architecture seam:** this needs a **new** seam — there is no existing config
  abstraction. `config.ts` sits beside `mailbox.ts`'s `Transport` interface and
  `handlers.ts`'s `HandlerDeps` as a third pure/DI seam: `broker/src/index.ts` and
  `bus/src/index.ts` both become thin callers of `resolveConfig`, exactly as `daemon.ts`
  already imports `isPidAlive` from `bus/src/registry.ts` — cross-package relative imports
  are an established pattern here, not a new one.
- **Code:** new `broker/src/config.ts` (+ `config.test.ts`); `broker/src/index.ts` (resolve
  config before `runForeground`, wire the fatal path, add the `config` subcommand);
  `bus/src/index.ts` (resolve config, pass `transport`/`channelsHome` into `createTransport`);
  `Makefile` (`mcp-add` drops `-e SESSIONBUS_TRANSPORT=$(TRANSPORT)`; `setup`/`launchd-install`
  need to ensure a config file exists with `transport: "socket"`, since the resolver's
  built-in default stays `"file"` to match the existing, currently-passing
  `bus/src/transport.test.ts` case "defaults to file when SESSIONBUS_TRANSPORT is unset").
- **Identity / beacons / inbox subscription:** untouched — no breaking risk on that axis.
- **Dependencies:** none added; `tokenCommand` execution uses Node's built-in
  `child_process`.
- **Ops:** the launchd plist is unchanged (already minimal). `make setup` gains
  responsibility for seeding `~/.claude/sessionbus/config.json`'s `transport` field (design
  decision, see design.md).
